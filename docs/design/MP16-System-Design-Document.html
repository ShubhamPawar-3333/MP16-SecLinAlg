1Purpose & scope#

This document describes how the Secure Linear Algebra Library is built. It converts the product requirements and backlog into a concrete architecture, module design, interface set, and verification plan that the three worklet teams can develop against in parallel and then integrate into one system.

How this document is organised

The material is split into three parts, matching the levels of design an evaluator looks for:

  • Part I — High-Level Design (§3–§7): the system in context, the layered architecture, the contracts between the three worklets, and how data moves through it.
  • Part II — Low-Level Design (§8–§11): the how, module by module — algorithms, public signatures, data structures, error types, and the complexity budget.
  • Part III — Quality, Security & Delivery (§12–§18): the security argument, non-functional targets, test plan, repository layout, risks, and traceability.

In scope for this document

  • The layered architecture and the dependency rules between layers.
  • The design of every module: responsibilities, key algorithms, public types, and errors.
  • The frozen interfaces between the three worklets, with pre- and post-conditions.
  • The secure-computation protocols (secret sharing, secure addition, Beaver-triple multiplication).
  • The error model, security argument, complexity budget, and test plan.
  • Traceability from each functional requirement to a module, a backlog story, and a test.

Out of scope

  • Product justification, personas, and market context — see the PRD (§2).
  • Sprint scheduling and story estimates — see the Backlog.
  • Any implementation that depends on an excluded library (NumPy, an MPC framework, floating point in the core). These are barred by the brief and fail review regardless of output.

Part I

High-Level Design

The what and the shape of the system: its context and users, the six-layer architecture and the dependency rules that hold it together, the frozen contracts between the three worklets, and the end-to-end data flow — including the one protocol the project exists to teach.

3System overview#

The library lets a developer choose a prime field, build vectors and matrices whose entries live in that field, perform exact linear algebra, and then run additive secret sharing and secure product operations on hidden values. The same algebra serves both plaintext and shared data — the secure layer adds protocols, not a second matrix implementation.

3.1What the system does

  • Exact field arithmetic. Add, subtract, multiply, and invert integers modulo a prime p, with no rounding anywhere.
  • Linear algebra over the field. Matrix multiply and transpose; Gaussian elimination and everything derived from it — rank, determinant, inverse, and solving Ax = b — with singular cases reported explicitly.
  • Secret-sharing primitives. Split a value into n additive shares, reconstruct it, and add shared values locally with no communication.
  • Secure products. A private inner product and a private matrix product on shared inputs, using a trusted dealer for shared×shared multiplication, each verified against the plaintext result.

3.2Users

UserNeeds from the system
Library user (developer)A clean, predictable API for exact linear algebra; typed errors on bad input; no cryptographic bookkeeping on the common path.
Protocol partySharing, reconstruction, and secure product operations that behave identically whether run by one simulated process or several.
Guide / evaluatorCode and notes that answer the learning-outcome questions directly — the security argument, the complexity derivation, the singular-case handling.

3.3Product goals this design serves

  • Every acceptance criterion in the backlog passes, with automated tests.
  • Zero excluded dependencies in the codebase.
  • Secure inner and matrix products reconstruct to the plaintext result across randomised tests.
  • Every learning objective can be defended in an individual viva.

4Architecture#

The system is a strict bottom-up stack of six layers. Each layer may use only the layer directly below it (and, for the secure layer, the trusted dealer). This is a graded design constraint, not a preference: the algebra must be fully testable with no cryptography present, and the secure layer must reuse the algebra unchanged.

4.2Technology stack

  • Language: Python 3, standard library only. C++ is acceptable if the team wants the performance exercise; standard library only either way.
  • Randomness: secrets module for share generation (uniform over [0, p)). random is acceptable for benchmark data only.
  • Testing: unittest or pytest (pytest is a dev dependency, not shipped in the library).
  • Timing: time.perf_counter for benchmarks.
  • No NumPy, SymPy, gmpy2, MP-SPDZ, database, ORM, web, cloud, or ML/AI library anywhere.

5Design principles & constraints#

5.1Principles

  1. Foundations-first. Every core concept — modular arithmetic, the inverse, matrix algorithms, sharing, triples — is implemented by the team. If a library would hide the concept, it is not used.
  2. Exactness. All arithmetic is over Z_p. No floating point appears in field, types, matmul, linalg, sharing, or secure.
  3. Layer independence. A layer never reaches around the one below it or imports from a layer above. The algebra has no knowledge of sharing.
  4. Parameterise the field. The prime is a value passed at field construction. It is never a module-level constant or a default baked into Matrix.
  5. Fail loudly. Every exceptional case — no inverse, wrong shape, singular matrix, inconsistent system, malformed shares — raises a specific typed error (§10). No silent None, no wrong answer.
  6. Contracts before code. The interfaces in §6 are frozen at the Week-3 review. Teams build against the published API, not another team's internals.

5.3Explicit exclusions

Numeric libraries (NumPy, BLAS/LAPACK); MPC or crypto frameworks (MP-SPDZ); floating-point arithmetic in the library; databases and ORMs; web frameworks and cloud services; machine-learning or AI libraries; malicious-adversary security; cryptographic triple generation without a trusted dealer.

Watch for
  • "Field" arithmetic done in floating point — results stop being exact and sharing breaks.
  • A modular inverse that returns a wrong value instead of raising when the element is not coprime to p.
  • Gaussian elimination that divides by a pivot instead of multiplying by its modular inverse.
  • Reconstruction that leaks the secret from a single share (e.g. non-uniform first shares).
  • Claiming a secure product is correct without a randomised check against the plaintext.
  • The prime hard-coded in Matrix so the API cannot be reused across fields.

Contract rules (all interfaces)

  • Stable names and types; a signature change is a versioned event.
  • Every public function has a docstring stating pre-conditions, post-conditions, and the errors it may raise.
  • Consumers depend on the published API only, never on a provider's private attributes.
  • Errors are typed classes from the shared hierarchy in §10, never bare ValueError or assert.
Decision — entry type at the boundary

Matrices and vectors expose FieldElement entries at the API boundary, even if they store raw ints internally for speed. This keeps types, linalg, and secure uniform and makes field-mismatch errors catchable. Revisit only if benchmarks show the wrapper is the bottleneck — and record the measurement if so.

7Data flow & protocols#

7.1End-to-end flow

A value enters the field; exact arithmetic runs; vectors and matrices are built from field elements; matrix algorithms run with no floating point. For the secure path, a value is split into additive shares, secure operations run locally on the shares (with triples for multiplication), and reconstruction recovers a result that must equal the plaintext computation.

7.2Secure multiplication with a Beaver triple

Addition and public scaling on shares are local and need no interaction. Multiplying two shared values is the one operation that does — and it is the concept the design is built to teach. The sequence below is one shared×shared multiply; the inner product repeats it once per term.

Part II

Low-Level Design

The how, one module at a time: responsibilities, key algorithms, illustrative public signatures, the concrete data structures behind the types, the full error hierarchy, and the complexity each operation must meet.

8Module detailed design#

Each module below lists its responsibility, the key algorithms, the public surface, and the errors it raises. Signatures are illustrative Python; the exact names and directions are the contracts fixed in §6.

8.1Field arithmetic W1

The foundation. Field(p) validates that p is prime and acts as a factory for FieldElement. Every element carries a reference to its field; operations between elements of different fields raise.

Algorithms

  • Reduction: any integer, positive or negative, is normalised into [0, p) by x % p (Python's % already returns a non-negative result for positive p).
  • Inverse: the extended Euclidean algorithm computes (g, s, t) with s·a + t·p = g. When g == 1, s mod p is the inverse; otherwise raise. Never search all values.
  • Division: a / b is defined as a · inverse(b).

Public surface

Field(p) -> Field
  .element(x: int) -> FieldElement      # reduces x into [0, p)
  .zero, .one -> FieldElement
  .random() -> FieldElement             # uniform in [0, p), via secrets

FieldElement
  __add__ __sub__ __mul__ __neg__ __eq__   # all reduce mod p
  inverse() -> FieldElement                # raises NoInverse for 0
  __truediv__(other) -> FieldElement       # self * other.inverse()

Errors

  • NoInverse — inverse() of 0, or of any element not coprime to p.
  • FieldMismatch — an operation between elements of two different fields.
  • NotPrime — Field(p) with composite or non-positive p.

Tests (FA-3)

Automated checks for associativity, commutativity, distributivity, additive and multiplicative identities, and inverses over p = 101; a check that a · inverse(a) == 1 for every non-zero a; a check that inverse(0) raises.

8.2Vector & Matrix types W1

Generic containers bound to a field at construction. Entries are stored as reduced integers or FieldElements (team's choice, subject to the boundary rule in §6). A Matrix is row-major; a Vector is a 1-D case with an orientation flag if the team needs row/column vectors.

Operations

  • add, sub — require matching shape, else ShapeError.
  • scalar_mul(k) — multiplies every entry by a field element.
  • transpose() — returns a new matrix, does not mutate the original.
  • __eq__ — compares field, shape, and all reduced entries.
  • __getitem__ / __setitem__ — bounds-checked indexing.

Invariants

  • Construction validates that a matrix is rectangular; a ragged row list raises ShapeError.
  • Shape is stored and queryable as .shape -> (rows, cols).
  • No operation mutates its operands; every result is a fresh object.

Tests (CT-3)

A + 0 == A, A · I == A, (Aᵀ)ᵀ == A, (A·B)ᵀ == Bᵀ · Aᵀ over p = 101.

8.3Matrix algorithms W1 W2

Multiplication Must (LA-1)

  • multiply(A, B) validates that A.cols == B.rows, else ShapeError.
  • Schoolbook triple loop; every accumulation is a field operation. Correct against hand-computed small cases.
  • A docstring states the O(n³) baseline and the exact operation count for an m×k by k×p product (m·k·p multiplications, m·p·(k−1) additions).

Gaussian elimination Must (LA-2)

  • Row-reduce to row-echelon form using modular inverses for pivot normalisation — never a floating-point division.
  • Pivot selection: take any non-zero entry in the current column. There is no stability-based choice because the arithmetic is exact.
  • Track row swaps to keep the determinant sign correct.
  • Return the echelon form plus the pivot list and swap count for the derived algorithms.

Rank, determinant, inverse Must (LA-3)

  • rank(A) = number of non-zero pivots.
  • determinant(A) = product of pivots × (−1)^swaps; 0 for a singular matrix.
  • inverse(A) = reduce [A | I] to [I | A⁻¹]; raise SingularMatrix when a pivot column has no non-zero entry.

Solve Ax = b Must (LA-4)

  • Reduce [A | b]. Return the unique solution when one exists.
  • NoUniqueSolution — the system is consistent but under-determined (free variables).
  • InconsistentSystem — a zero row on the left with a non-zero right-hand side.

Strassen Could (LA-6)

Optional. If taken: identical results to schoolbook on random inputs; a benchmark records the crossover size with a written trade-off note. Time here is secondary to the secure layer and its tests.

8.4Secret sharing W3

Additive n-out-of-n sharing over the field. A share set is an ordered tuple of n field elements tagged with the field and the party count.

Algorithms

  • Split share(v, n): draw s₁ … s₍ₙ₋₁₎ uniformly from [0, p) using secrets; set sₙ = v − (s₁ + … + s₍ₙ₋₁₎) mod p.
  • Reconstruct reconstruct(shares): return Σ sᵢ mod p.
  • Local secure addition add_shares(u_shares, v_shares): party i computes uᵢ + vᵢ. The result is a valid sharing of u + v because the map v ↦ (s₁,…,sₙ) is linear over the field.

Public surface

share(v: FieldElement, n: int) -> ShareSet
reconstruct(shares: ShareSet) -> FieldElement
add_shares(a: ShareSet, b: ShareSet) -> ShareSet          # local, no communication
scalar_mul_shares(k: FieldElement, a: ShareSet) -> ShareSet
add_public(c: FieldElement, a: ShareSet) -> ShareSet       # add constant to one share

Errors

  • ShareCountMismatch — combining share sets with different n.
  • FieldMismatch — share sets over different fields.

Tests (SS-2, SS-3, SS-4)

Round-trip reconstruct(share(v, n)) == v for many random v, n; the n−1-privacy argument (see §12) backed by a distribution check on any n−1-subset; reconstruct(add_shares(share(u), share(v))) == u + v.

8.5Secure computation W3

Trusted dealer (SP-1)

Dealer(field, n) produces a Beaver triple as three share sets ([a], [b], [c]) with reconstruct([c]) == reconstruct([a]) · reconstruct([b]). The dealer is a documented mini-project simplification standing in for real triple generation; it must be named as such in the security write-up (SP-4).

Shared × shared multiplication

To multiply shared [x] and [y] using one triple ([a], [b], [c]):

  1. Locally form [d] = [x] − [a] and [e] = [y] − [b].
  2. Open d and e — reconstruct them in the clear. Safe: a and b are uniform, so d and e are uniform masks that carry no information about x or y.
  3. Locally combine: [xy] = [c] + d·[b] + e·[a] + d·e, where the constant d·e is added to one designated party's share.

Correctness (reconstructed): c + d·b + e·a + d·e = ab + (x−a)b + (y−b)a + (x−a)(y−b) = xy. This identity is exactly what the viva asks the team to derive.

Private inner product Must (SP-2)

  • Public×shared terms are computed locally with scalar_mul_shares.
  • Each shared×shared term consumes one triple via the step above.
  • The k product shares are summed locally; reconstruct equals the plaintext dot product on random inputs.

Private matrix product Should (SP-3)

Built from the private inner product over the rows of the left matrix and the columns of the right. An m×k by k×p product consumes m·k·p triples. Reconstruction equals the plaintext matrix product on random inputs.

Multiplication boundary Must (SP-4)

A short write-up states which operations are local and free (addition, public scaling), which need a triple (shared×shared), and exactly where a real MPC protocol would be required beyond this scope (triple generation, malicious security, networking).

8.6Verification & benchmarking W3 + all

  • VB-1 Must: for random inputs, reconstructed secure inner and matrix products equal the plaintext results. Run with a fixed seed for reproducibility plus a few unseeded rounds.
  • VB-2 Should: matrix-multiply timings across increasing n, recorded as a table and a short plot description; if Strassen is done, the crossover point is recorded.

10Error-handling model#

All library errors derive from one base class so a caller can catch broadly or narrowly. Errors are raised at the layer that detects the violation, with a message that names the offending values.

SecLinAlgError                 (base)
├── FieldError
│   ├── NotPrime                Field(p) with composite p
│   ├── NoInverse               inverse() of 0 or non-coprime element
│   └── FieldMismatch           operands from different fields
├── ShapeError                  non-rectangular / dimension mismatch
├── SingularError
│   ├── SingularMatrix          inverse() of a non-invertible matrix
│   ├── NoUniqueSolution        consistent but under-determined system
│   └── InconsistentSystem      no solution exists
└── ShareError
    ├── ShareCountMismatch      combining share sets with different n
    └── TripleExhausted         shared×shared multiply with no triple available
Rule

No assert in library code paths (asserts vanish under -O). No returning None or a sentinel to signal failure. Every documented failure mode has a test that asserts the specific error type is raised.

12Security design#

12.1Threat model

Honest-but-curious. Every party follows the protocol exactly but may inspect everything it receives. Parties do not collude beyond holding up to n−1 shares between them. There is no active tampering, no dropped messages, no timing side channels. All parties run in one process for the mini-project; the model is what would hold if they were separate.

Out of scope: malicious parties, n-of-n collusion, real triple generation, and network-level adversaries. The write-up must say so plainly (SP-4).

12.2Why a finite field, not floating point

Secret sharing needs reconstruct(share(v)) == v to hold exactly. Floating point cannot promise that — s₁ + s₂ + s₃ may not equal v after rounding, and the masks in a Beaver triple would not cancel. A finite field gives exact arithmetic and a well-defined inverse for every non-zero element, which is also what Gaussian elimination needs to divide by a pivot.

12.3Why n−1 shares reveal nothing

By construction, s₁ … s₍ₙ₋₁₎ are drawn independently and uniformly from Z_p, and sₙ = v − Σ sᵢ. Take any subset of n−1 shares:

  • If it is exactly {s₁ … s₍ₙ₋₁₎}, those are uniform and independent of v by definition.
  • If it includes sₙ, then the one missing share sⱼ (j < n) is uniform and appears in sₙ = v − Σ sᵢ, acting as a one-time pad: for every candidate secret v' there is exactly one value of sⱼ consistent with the observed n−1 shares. So the observed shares are uniform on (Z_p)^{n−1} regardless of v.

Either way the marginal distribution of any n−1 shares is the same for every secret, so they carry no information. The test in SS-3 checks this empirically by fixing a subset and confirming its distribution does not shift with v.

12.4Why opening d and e is safe

In Figure 3, d = x − a and e = y − b where a, b are uniform and secret. d and e are therefore uniform over Z_p and independent of x, y — revealing them is revealing two random numbers. The secret inputs stay hidden; only the final result is reconstructed.

Security — what the demo must show

Print the shares of a secret and show any one (or n−1) is indistinguishable from random. Run a secure inner product, show the parties only ever exchange opened masks, reconstruct the result, and compare it to the plaintext dot product. State which step would need a real protocol outside this scope.

14Testing strategy#

Tests are evidence, not an afterthought. Each test is tagged with the acceptance criterion it proves. Hard cases — singular matrices, non-invertible elements, single-share privacy — are written early.

Field tests/field/

  • Reduction of positive, negative, and large integers.
  • Field laws: associativity, commutativity, distributivity, identities.
  • Inverse of every non-zero element at p = 101; inverse(0) raises.

Types & matrix tests/matrix/

  • Shape validation; non-rectangular input raises ShapeError.
  • Identities: A+0=A, A·I=A, (Aᵀ)ᵀ=A, (A·B)ᵀ=Bᵀ·Aᵀ.
  • Multiply against hand-computed 2×2 and 3×3 cases.
  • Gaussian elimination with row swaps and zero pivots.
  • Rank / determinant / inverse for regular and singular matrices.
  • Solve: unique, under-determined, and inconsistent systems each raise the right result or error.

Secure tests/secure/

  • Share / reconstruct round trip for many random v, n.
  • n−1-share distribution does not shift with the secret.
  • Secure addition reconstructs to u + v.
  • Dealer triple satisfies c = a·b after reconstruction.
  • Private inner product vs. plaintext dot product, randomised.
  • Private matrix product vs. plaintext matrix product, randomised.

Cross-cutting

  • Every suite runs from one command and reports pass/fail per criterion.
  • Same matrix suite runs at p = 101 and p = 2³¹−1.
  • A grep check in CI fails the build on an excluded import.
  • Benchmarks live in benchmarks/, separate from functional tests.

18Open questions#

  • Party simulation in the demo. Show n explicit simulated party objects, or reconstruct within one object? Explicit simulation makes a stronger viva — recommended, decision needed before Worklet 3 integration.
